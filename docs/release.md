# 版本与发布

> 本文是版本号与发布规则的唯一权威；CI 实现（`tools/release_tag_check.py` 与 `.github/workflows/release.yml`）与本文不一致时，以本文为准。

系统里有两个版本号，各司其职：

| | 给谁看 | 长什么样 | 谁来定 |
| --- | --- | --- | --- |
| 版本名 VersionName | 人 | `26.08.2`、`26.08.2-rc1` | 发版时人工填写，CI 校验 |
| 版本码 VersionCode | Android 系统 | `26082301` | 发布流水线自动分配，人不用管 |

Android 只靠版本码判断"哪个更新、能否覆盖安装"；用户看到的一律是版本名。

## 版本名 `YY.MM.PATCH[-rcN]`

- **YY.MM** = 发布年月，必须等于打 tag 时所在的年月（固定按 Asia/Shanghai）。
- **PATCH** = 当月用到的第几个版本号，从 1 开始；新号永远取"该月已有最大号 + 1"（候选也占号），不跳号、不复用；在已开的号上续发 rc 或定稿不受此限。每月从 1 重来，某月没发版就直接跳过。
- **-rcN**（可选）= 候选版。对某个号没把握时，先发 `…-rc1`、`…-rc2`… 逐个修复验证，最后发同号无后缀的**正式版**收尾。也可以不用候选，直接发正式版。

四条硬规则（CI 强制）：

1. **tag 不可变**——打出的 tag 不能修改、不能删除重建。发错了不撤回，用下一个号发新版修复。
2. **正式版即封版**——某个号一旦发过正式版，就定型：不能再补候选，也永不再用。
3. **候选只进不退**——`rc1` 之后只能是 `rc2`，不许跳号、回退或原地重发。
4. **候选当月收尾**——"年月 = 发布月"的直接推论：月底前没验完的候选作废，下月换新号重走（所以月底、尤其 12 月底，别开新候选）。

同一时刻并行开多个候选也没问题：各占各的号，互不影响，各自收尾。

### 示例（2026 年 8 月）

| 操作 | 版本名 |
| --- | --- |
| 当月首发，直接正式 | `26.08.1` |
| 想先验证：候选 #1 | `26.08.2-rc1` |
| rc1 有 bug，修复重发 | `26.08.2-rc2` |
| rc2 验证通过，定稿 | `26.08.2` |
| 再发下一个 | `26.08.3` |

## 版本码 `YYMMDDNN`

8 位数字 = 发布日期（时区同上）+ 当天第几个发布构建（`NN` 两位序号，单日最多 99 个——两位序号的容量上限，实际触不到）。

- 由发布流水线在构建时分配：统计当天已发的个数再 +1，并校验结果大于历史最大版本码（防计数或时钟异常导致回退）。
- 全程严格递增，意味着新构建总能覆盖安装旧构建——候选版也能直接覆盖正式版（候选必然比上一个正式版发得晚）。手动分发下这正是想要的效果。

## tag 与 Release

- 只有发布流水线打 tag：**注解 tag**，名为 `v<版本名>`，消息体带一行 `VersionCode: xxxxxxxx`——流水线靠它统计"当天已发几个"，不需要任何额外状态。
- Release 先建 **draft**，人工确认后正式发布；带 `-rc` 的自动标记为 Pre-release。
- 附件为签名 APK，命名 `MCPocket-<版本名>.apk`，变更说明自动生成。

## 发布步骤

唯一入口：GitHub Actions 的 **Build & Release** 工作流（网页手动触发）。

1. Run workflow，填版本名（如 `26.08.2-rc2`，`v` 前缀可省）；
2. CI 校验上述全部规则并分配版本码，不合格立即失败，不留任何 tag / Release；
3. 构建签名 APK → 打 tag → 建 draft Release；
4. 人工确认，发布。

顺序保证：构建成功才打 tag，构建失败不会留下孤儿 tag。反过来，若 tag 已打出、后续步骤（如建 Release）才失败，这个号也已被占用——重发时用下一个号。

## 本地构建

- 本地与 PR 构建一律 `versionName = "dev"`、`versionCode = 1`，与发布规则完全无关；发布构建的这两个值由流水线覆写，本地值不会进入产物。
- 本地想临时自定义版本名：`-PversionName=dev-xxx`（仅影响本地产物，不参与发布规则）。
- 想覆盖已安装的发布版做调试：`-PversionCode=99999999`（8 个 9，大于一切正常版本码）。副作用：装过它之后正常发布版反而覆盖不上了，换回正式版需卸载重装。

## FAQ

- **正式版出了致命 bug？** tag 不可变：当月内用下一个 PATCH 发修复版，已跨月就下月新号。没有专门的 hotfix 号段——"修复也是一个普通的下一个号"。
- **rc1 发现 bug？** 发 `rc2` 修复后定稿；不能原地重发 `rc1`。
- **某个月一个版都没发？** 无影响，下月 PATCH 从 1 重新计。
- **跨年（`26.12` → `27.01`）？** 版本码含年份，天然递增，无边界问题。
- **月底/零点边界竞态？** 校验在构建前、打 tag 在构建后：若校验时是本月最后一天 23:xx，tag 实际创建已跨零点（甚至跨月），其创建时间会与校验判定的月份不一致，该链后续会被判为跨月。触发概率极低，属已知边界，不做处理。
